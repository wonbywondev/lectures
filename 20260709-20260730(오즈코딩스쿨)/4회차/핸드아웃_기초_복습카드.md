# 🌱 4회차 복습 카드 — 집에서 오늘 순서 그대로

> 오늘 놓친 부분이 있어도 괜찮아요. 이 카드만 있으면 **혼자 처음부터 끝까지** 다시 할 수 있습니다.
> **회색 상자 안의 문장을 그대로 복사**해서 Claude에게 붙여넣고 Enter만 누르면 돼요.
>
> 💡 실행은 오늘과 똑같이 **Claude Desktop 앱 `Code` 탭**에서. **미니당근 폴더**를 열고 시작하세요.

> 🎯 **오늘의 목적지:** 남에게 보낼 수 있는 **주소(URL)** 하나. 그런데 진짜 볼 건 배포가 아니라 — **내보내기 전에 다듬는 순서**입니다.

---

## 📌 시작 전에 — 오늘의 큰 그림

배포는 **명령 한 줄**이에요. 진짜예요.

```
firebase 배포해줘. URL 알려줘
```

그런데 오늘 2시간을 이거 하나에 쓰진 않죠. **내보내기 전에 다듬을 게 있어서**입니다. 네 가지를 순서대로 다듬습니다.

| | 다듬기 | 왜 |
|---|---|---|
| ① | **겉모습** | 기능은 되는데 못생겼다 → 앱 손보고 **랜딩 만들기** |
| ② | **검색되게** | 만들어도 아무도 못 찾으면 없는 것 |
| ③ | **법 · 약속** | 남의 정보를 받으니까 |
| ④ | **문 열기** | 배포 → 내 주소 |

> ⚠️ **오늘의 규칙:** 매 단계 끝에 **👀 내 눈으로 확인.** 3회차에 배웠죠 — 만든 사람 말만 믿지 않습니다. 만든 게 AI라도 똑같아요.

# STEP 0. 지금 화면 보고, 세이브부터

먼저 **지금 상태를 눈에 담아둡니다.** 나중에 비교할 거니까요.

```
미니당근 로컬 서버로 띄우고 브라우저로 열어줘
```
> ✅ **확인:** 브라우저에 미니당근이 뜨면 성공. 기능은 되는데 **밋밋하죠?**

디자인을 갈아엎기 전에 **되돌아올 지점**을 만듭니다.

```
지금 커밋에 day4-before-polish 태그 붙여줘
```
> ✅ **확인:** 태그 완료 답이 오면 성공.
> 💡 마음에 안 들면 언제든 → `day4-before-polish 태그로 되돌려줘` 한 줄. **되돌릴 수 있으니 과감해집니다.**

# STEP 1. taste-skill — 점검하고 설치하기

**AI가 만든 화면은 왜 다 비슷할까요?** 보라·파랑 그라디언트, 3등분 카드, 새까만 배경 — AI에겐 **기본값**이 있어서 그냥 시키면 그게 나옵니다. 이런 결과물을 **AI slop**이라고 불러요. 앞으로 자주 보실 단어입니다.

**taste-skill**은 그 기본값을 **막아주는** 스킬이에요. 그런데 좋아 보인다고 바로 설치하지 않습니다.

**① 먼저 점검부터** (3회차에 배운 그대로)

```
https://github.com/Leonxlnx/taste-skill 이거 설치하려고 해.
설치 전에 먼저: 뭘 하는 스킬인지 요약하고,
내 파일을 함부로 지우거나 기능을 깨뜨릴 위험은 없는지,
외부로 뭘 보내지는 않는지 점검해줘. 아직 설치는 말고
```
> ✅ **확인:** 기능 요약 + 위험 여부 보고가 나오면 성공. **아직 설치 안 됐습니다.**

**② 괜찮으면 그때 설치**

```
괜찮네. 설치해줘.
```
> ✅ **확인:** 설치 완료 답이 오면 성공.
> 🆘 **설치가 막히면** → `npx skills add [주소]로 설치해줘` 라고 다시 시키세요. AI가 *"직접 치셔야 해요"* 라고 하면 이 문장으로 되받으면 됩니다.

> ⚠️ 디자인 스킬은 **내 화면 파일을 직접 고칩니다.** 그래서 STEP 0에서 태그부터 찍은 거예요.

# STEP 2. 시안 3개 받고 — **고르는 건 내가**

```
우리 프로젝트에 맞는 디자인 시안을 taste-skill로 3개 만들어서 보여줘.
말로만 말고 샘플 화면으로 볼 수 있게.

각 안마다: 어떤 느낌인지 한 줄, 색 조합, 폰트, 그리고 왜 그렇게 골랐는지도 같이.
서로 확실히 다른 방향으로 부탁해
```
> ✅ **확인:** 서로 다른 **3개 샘플**을 눈으로 비교할 수 있으면 성공.

**여기가 오늘의 핵심입니다.**

- **우리 손님이 누구죠?** 동네 사람들, 폰으로 씁니다 — 그 기준으로 고르세요
- 안 맞으면 **섞어도 됩니다** — *"1번 구성에 2번 색으로"*
- AI 제안은 **출발점**이지 정답이 아니에요. 좋은 건 받고, **브랜드는 내가 지킵니다**

> 💡 시안을 받으면 먼저 이런 한 줄이 나옵니다 — *"이건 ○○를 위한 ○○ 페이지로 읽었습니다."* **뭘로 이해했는지 먼저 말하는 것**이니, 틀렸으면 그때 잡으면 됩니다.

# STEP 3. 확정한 안으로 앱 디자인 개선

고른 번호로 시킵니다. (아래는 2번을 골랐을 때)

```
2번째 안으로 앱 화면을 다듬어줘.
기능은 절대 깨뜨리지 말고, 뭘 바꿨는지 알려줘
```
> ✅ **확인:** 수정 로그가 흐르면 정상. **기다리지 말고** 다음으로 넘어가세요.

**확정한 방향은 글로 남겨두세요.** `DESIGN.md`로 적어두면 **다음 작업에서도 AI가 참고**합니다. 2회차에 PRD로 *기능의 의도*를 줬듯, DESIGN.md는 *디자인의 의도*예요.

```
DESIGN.md 파일을 만들어줘. 우리 서비스 디자인 방향이야:
- 동네 중고거래라 따뜻하고 친근한 느낌
- 당근 느낌의 주황색을 포인트로
- 글씨는 크고 읽기 쉽게
```
> ✅ **확인:** `DESIGN.md`가 생기면 성공. 위 세 줄은 예시니 **여러분 서비스 방향으로 바꿔** 쓰세요.
> 💡 *"저 사이트처럼 만들어줘"* 를 파일로 바꿔주는 곳도 있습니다 — `https://getdesign.md` (브랜드 300여 개 분석본)

# STEP 4. 랜딩페이지 만들기

**랜딩페이지가 왜 필요한가** — 앱 주소를 그냥 보내면 상대는 **이게 뭔지 모릅니다.** 회원가입 화면만 보이죠.

| | 앱 | 랜딩페이지 |
|---|---|---|
| 역할 | **쓰는 곳** | **보여주는 곳** |
| 비유 | 가게 안 | **간판 · 쇼윈도** |
| 목적 | 기능을 쓴다 | 30초 안에 뭐 하는 서비스인지 알리고 **한 가지 행동**으로 |

> 💡 **창업가에게:** 사실 **앱보다 랜딩이 먼저 필요한 경우가 많아요.** 사전예약이나 문의만 받아도 아이템 검증이 시작되니까요.

```
같은 디자인 방향으로 미니당근 랜딩페이지를 만들어줘. landing.html 한 장으로.
배포할 때 앱이랑 같이 올라가는 위치에 만들어줘.

이런 내용이 들어가면 좋겠어:
- 한눈에 뭐 하는 서비스인지 (동네 중고거래)
- 주요 기능 세 가지 (상품 등록 / 실시간 채팅 / 안전한 거래)
- 앱으로 이동하는 버튼 하나

로컬에서 열어볼 수 있게 만들어줘
```
> ✅ **확인:** `landing.html`이 생기고 **브라우저로 열면 랜딩이 보이면** 성공.

**이 명령에 네 가지가 들어 있습니다** — 다음에 여러분 아이템으로 할 때도 이 네 개만 챙기면 됩니다.

| | 조각 | 왜 |
|---|---|---|
| 1 | 파일 하나로, **배포에 같이 실리는 자리**에 | 안 그러면 만들어도 배포에 안 올라갑니다 |
| 2 | **내용은 내가 정한다** | "알아서 잘"이 아니라 뭐가 들어갈지 |
| 3 | **행동은 하나** | 버튼이 여러 개면 아무것도 안 누릅니다 |
| 4 | **확인할 방법까지** | 못 열어보면 못 고칩니다 |

> 💡 **뭘 넣을지 막히면** 3회차의 brainstorming으로 같이 정해도 됩니다 — *"랜딩에 어떤 내용이 들어가야 할지 brainstorming으로 같이 구상하자"*

# STEP 5. 만든 스킬에게 **다시 검사**시키기

```
taste-skill의 출고 전 점검(pre-flight check)으로 앱이랑 랜딩 둘 다 훑어줘.
걸리는 항목이 있으면 고치고, 뭘 바꿨는지 알려줘
```
> ✅ **확인:** 점검 항목별 통과·실패가 나오면 성공 — *"강조색 일관성 OK"*, *"같은 뜻의 버튼 두 개 발견 → 하나로"* 같은.

> 💡 이 스킬엔 **출고 전 검사표**가 따로 있습니다. 강조색이 페이지 내내 같은지, 밝기 테마가 중간에 뒤집히진 않는지 같은 것들.
> **만든 게 AI라도 만든 사람 말만 믿지 않는다** — 그래서 검사표가 있는 도구를 골랐습니다.


# STEP 7. 점수로 확인하기 — lighthouse

**lighthouse**는 구글이 만든 무료 웹 검사기예요. 따로 설치할 것 없이 그때그때 받아서 실행됩니다.

```
lighthouse로 방금 만든 랜딩페이지 검사해줘. 점수 알려주고, 낮은 항목이 뭔지 설명해줘
```
> ✅ **확인:** 네 가지 점수가 나오면 성공 — **성능 / 접근성 / 권장사항 / SEO**
> ⏱ **1분쯤 걸립니다.** 크롬을 새로 띄워 페이지를 실제로 열어보는 검사라 시간이 걸려요. **돌려놓고 기다리면 됩니다.**

> 💡 **랜딩에선 SEO가 특히 중요합니다.** 앱은 검색으로 들어올 일이 적지만, 랜딩은 **검색으로 들어오라고 만든 것**이니까요.

# STEP 8. 검색되게 만들기 — SEO

```
랜딩페이지 SEO 고쳐줘.
제목·설명, OG 이미지,
robots.txt랑 사이트맵까지. 뭘 넣었는지 알려줘
```
> ✅ **확인:** 고친 항목 목록이 나오면 성공.

**이 명령에 네 가지가 들어 있습니다.**

| | 조각 | 뜻 |
|---|---|---|
| 1 | **SEO** | 검색 엔진 최적화. 구글·네이버에서 우리 페이지가 잘 뜨게 손보는 일 전부 |
| 2 | **제목 · 설명** | 검색 결과에 뜨는 문구. 미리보기 카드에도 같이 나옵니다 |
| 3 | **OG 이미지** | 카톡에 링크 붙이면 뜨는 **미리보기 카드**. 없으면 밋밋한 파란 링크만 |
| 4 | **robots.txt · 사이트맵** | 검색엔진에게 "여기 있어요" 알려주는 파일 |

> 🔗 **배포 후 확인** — 카카오 공유 디버거 `https://developers.kakao.com/tool/debugger/sharing`
> 내 URL을 넣으면 **카톡에 어떻게 뜰지 미리** 볼 수 있어요.

# STEP 9. AI 검색에도 걸리게 — FAQ

요즘은 검색을 **AI한테** 하죠. *"동네 중고거래 앱 뭐 좋아?"* 그럼 **그때 우리가 나와야** 합니다. 이걸 **AEO** 또는 **GEO**라고 불러요 (둘은 거의 같은 뜻으로 섞어 씁니다. 외울 필요 없어요).

**하는 일은 하나** — 질문–답변 형태로 명확하게 써두기.

```
랜딩페이지에 FAQ 섹션 추가해줘.
"어떤 서비스인가요", "무료인가요", "어떻게 시작하나요" 같은 질문 5개 정도.
그리고 AI 검색이 참조하기 좋게 FAQ 구조화 데이터(FAQPage 스키마)도 같이 넣어줘
```
> ✅ **확인:** 랜딩에 FAQ가 생기면 성공.
> 📊 FAQ 구조화 데이터를 넣은 페이지가 **AI 답변에 3.2배 더 등장**한다는 조사가 있습니다.

점수가 올랐는지 다시 재봅니다.

```
lighthouse 다시 돌려줘
```
> ✅ **확인:** 점수가 올랐으면 성공. 안 올랐으면 → *"왜 안 올랐는지 설명해줘"*

```
지금까지 작업 커밋해줘. 뭘 했는지 메시지에 남기고
```

# STEP 10. 법 · 약속 — 처리방침과 이용약관

**집에서 친구 초대해 요리해주는 것**과 **식당을 차리는 것**은 다릅니다. 친구는 좀 짜도 웃고 넘어가지만 손님은 돈 내고 오죠. 집에선 아무도 안 묻는데 식당은 **위생 기준·영업신고**가 있습니다 — **책임이 붙는 겁니다.**

3회차에 *"보안은 기능이 아니라 신뢰"* 라고 했죠. **처리방침은 그 신뢰의 문서**이고, **법으로 요구**됩니다.

**① 먼저 점검** (법률 도구는 더 깐깐하게)

```
https://github.com/kimlawtech/korean-privacy-terms 이거 쓰려고 해.
설치 전에 기능이랑 보안 점검해줘. 아직 설치는 말고
```
> ⚠️ **뒤집어 생각하기:** 법률 도구가 *"이건 초안이고 법적 책임은 못 진다"* 고 **스스로 밝히는 게 정상**이에요. 그런 안내가 없으면 오히려 의심하세요.

**② 만들어서 랜딩에 붙이기**

```
korean-privacy-terms 스킬로 개인정보처리방침이랑 이용약관을 만들어서
랜딩페이지에서 볼 수 있게 붙여줘
```
> ✅ **확인:** 질문이 **하나씩** 오면 성공. 막히면 → *"잘 모르겠어. 이런 서비스면 보통 어떻게 하는지 추천해줘"*

**③ 👀 링크만 보지 말고 읽어보세요**

- 랜딩 아래 링크가 보이고, **눌러서 내용이 뜨나?**
- **내용이 우리 서비스랑 맞나?** 수집 안 하는 걸 수집한다고 써 있으면 안 되잖아요
- **이건 초안입니다.** 실제 사업이면 최종본은 사람이 확인 — **법률 문서일수록 검수는 내 몫**

```
지금까지 작업 커밋해줘. 뭘 했는지 메시지에 남기고
```

# STEP 11. 문 열기 — 배포

```
firebase 배포해줘. 랜딩페이지랑 앱 둘 다 올라가게 하고, URL 알려줘
```
> ✅ **확인:** `프로젝트명.web.app` 같은 **URL이 나오면** 성공.
> 💡 랜딩이 새로 생겼으니 **배포 설정도 바뀌어야** 합니다. 그걸 *"둘 다 올라가게"* 한마디로 시킨 거예요.
> ⚠️ Firebase 계정·플랜 상황에 따라 막힐 수 있어요. 안 되면 다음에 다시 — 핵심은 **배포가 명령 한 줄**이라는 사실입니다.

**👀 마지막 눈 검수 — URL 나왔다고 끝이 아닙니다**

1. **내 폰**으로 접속 → 랜딩이 뜨나?
2. **카톡으로 나에게 링크 보내기** → 미리보기 이미지·제목이 뜨나? (STEP 8에서 고친 것)
3. **앱으로 이동** 버튼 → 상품 등록·채팅 되나?
4. 옆 사람 URL로도 들어가 보기

> ⚠️ **로컬에선 됐는데 배포하니 안 되는** 경우가 있어요. 환경이 다르거든요.

마지막으로 이름표를 남깁니다.

```
지금 커밋에 day4-done 태그 붙여줘
```

> 🔗 **도메인은 사람이 삽니다** — 카드 결제·본인인증은 **AI에게 못 맡깁니다.** 1회차 firebase 로그인 때와 같은 자리예요. **CLI 위임에도 경계가 있습니다.**

## 🎒 프롬프트 벨트 — 회차 순이 아니라, 일하는 순서

다음 프로젝트에서 **위에서부터 그대로** 쓰세요.

| 단계 | 프롬프트 |
|---|---|
| 0 · 시작 | `이 폴더에서 새 프로젝트 시작할 거야. 폴더 확인하고 git으로 관리 시작해줘` |
| 1 · 구상 | `~을 만들고 싶어. brainstorming으로 같이 구상하자` |
| 2 · 의도 | `PRD ⑨에 이 줄 채워줘` / `DESIGN.md 만들어줘` |
| 3 · 발사 | `바로 진행해줘. TDD로 진행해줘. 단계마다 커밋하고 태그도 달아줘` |
| 4 · 검수 | `/code-review` · `/security-review` · `/check [기능]` · `lighthouse로 검사해줘` |
| 5 · 고치기 | `방금 검수에서 나온 것 중 중요한 것부터 고쳐줘` |
| 6 · 출시 | `처리방침 만들어줘` · `SEO 고쳐줘` · `firebase 배포해줘` |
| 🆘 되돌리기 | `방금 커밋으로 되돌려줘` / `[태그]로 되돌려줘` |
| 🔍 최신 확인 | `context7으로 최신 방법 확인해서 알려줘` |
| 📦 새 도구 | `이거 설치 전에 기능·보안 점검부터. 아직 설치 말고` |

> 💡 `/security-review`에서 **`origin/HEAD` 에러**가 나면 — 깃허브에 안 올린 프로젝트라서 그렇습니다. 이렇게 다시 시키세요: *"깃허브에 안 올린 프로젝트라 그래. 지금 커밋 안 된 변경만 보안 점검해줘"*
